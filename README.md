# 四边扫描去黑边

这是一个完全在浏览器本地运行的 PWA 原型，适合在 iPhone 17 的 Safari 中使用。

## 算法

- 先按"近黑"标准给每一行、每一列分类：像素 RGB 最大值不超过黑色阈值，并且该行/列中达到这个标准的像素比例不低于覆盖率阈值。
- 再找出**包含图像几何中心**的那一段连续"非近黑"内容，把它当作主体。四条边的裁剪量就是从这个中心段向上下左右量出去——凡是中心段之外没有连续内容的区域，一律裁掉。上、下、左、右四条边独立判断。
- 如果几何中心本身就落在黑区里（例如"界面工具条 + 长条黑边"把中心包住的截图，照片只占画面下半部分），说明"中心必在主体内"这个前提不成立，此时退化为取最长的一段连续内容，仍然能得到正确的主体。
- 只有当一条边需要裁掉的条带中，近黑行占比**严格过半**时才真正裁剪。不过半说明黑条是夹在画面中间的暗色物体（例如主体内部的黑色区域），为了它切掉外侧真正的内容不划算，此时保留原样交给手动微调；占比正好一半时按不裁处理（保守）。
- 单边最多裁掉轴长的 75%，保证主体至少还留下 1/4，作为兜底保护。
- 整幅近乎全黑时找不到主体，不做任何裁剪；过细的黑线由"最小黑边厚度"过滤掉。

这条路线不再依赖"图像中心一定落在主体内"这个假设。早期版本从图像中心向外扫描，遇到中心被黑区包住的截图时，扫描起点本身就落在黑区里，代码会把中心误判成黑边的内侧边缘，算出接近半个画布的裁剪量后被安全上限否定，最终四条边都不裁。

### 深色界面栏识别（v1.1 新增）

在相册、社交类 App 里看图时截图，画面顶部会带上应用自身的深色界面：状态栏、"‹ 返回 / 页码 / 投诉"导航栏，以及照片上下的黑留白。这类区域的颜色是纯黑 `(0,0,0)` 或去饱和深板岩 `(40,45,55)`，**最大通道 55 高于默认黑色阈值 42**，所以上面的近黑判据完全看不见它，会把整块界面当成内容保留下来。

因此增加一路独立判据，与近黑判据并列，其余机制（内容段、中心锚定主体、纯度保护、上限保护）全部原样复用：

1. **单行判据（平坦深色）**——三个条件同时满足才算界面栏行：
   - 行**中位数**不超过 72。用中位数而非均值是关键：界面栏是"暗底 + 少量白字"，白字会把行均值抬到 73~78 并在阈值附近摆动，而行中位数稳定在 55~66；照片行的中位数就是照片自身颜色。
   - 落在中位数 ±12 内的像素占比不低于 78%。界面栏是纯色块，照片有纹理。
   - 亮像素（≥150）占比不超过 10%，即只允许少量文字笔画。
2. **贴边游程**——只有从图像边缘起连续的界面栏才被采纳。这样即使照片中部出现一条平坦暗带，也不会被误判而把画布切碎。游程内允许 8 行间断（抗锯齿过渡行、渐变），连续间断超过该值即判定已进入照片内容；游程末端回退到"最后一个界面栏行"之后，避免把照片内容一并吞掉。游程长度不足 20 个采样行、或其中界面栏行占比低于 80%，都不采纳。
3. **对比度护栏**——界面栏之后的第一行必须明显更亮（≥100，或达到界面栏亮度中位数的 1.6 倍），否则说明这只是照片自身的暗部，保守放弃。

第 3 条是这套判据的主要失效边界。已知的两种保守放行情形：

- 照片顶端本身就是一块平坦暗色区域，且没有明显亮度阶跃；
- 界面栏下沿是一条跨度较大的渐变（超出 8 行容错窗口），例如某些 App 的渐变遮罩。跨度 ≤3px 的抗锯齿软边不受影响，仍能正常裁掉。

这两种情况下算法**不会多裁**（结果与关闭开关时一致），界面栏只是保留下来，交给手动微调。若遇到，可在“检测参数”里关掉“界面栏”开关，或用“边界微调”的负数向回缩。

## 在 iPhone 上使用

1. 将此目录部署到任意支持 HTTPS 的静态网站，或在电脑上运行 `python3 -m http.server` 后用同一 Wi-Fi 访问。
2. 在 iPhone Safari 打开页面。
3. 点击“选择图片”，一次选择多张截图。
4. 所有图片会自动独立检测上、下、左、右四条边。
5. 默认检测参数已折叠；需要调整时点击“展开参数”。松开参数滑块或切换检测方向后自动应用，也可以点击“重新检测”。边界微调范围为 -5～30px，默认 0；负数仅对检测到黑边的方向向内多裁，正数保留边距。同一面板里的“界面栏”开关默认开启，控制是否把应用自身的深色状态栏、导航栏与黑留白一并裁掉；若某张图照片顶端本身就是平坦暗色而被误裁，关掉它再点“重新检测”即可。
6. 查看实际裁剪量与输出尺寸；必要时在对应图片里展开“手动微调四边”，修改数值并离开输入框后更新预览。重新应用检测参数会覆盖手动调整。
7. 点击页面顶部“保存全部”。
8. iPhone 系统分享面板中选择“存储图像”，一次保存全部处理后的图片。

网页不能绕过 iOS 权限直接写入照片库，因此最后一步仍由系统分享面板确认。若浏览器不支持多文件分享，可使用“逐张下载”。

首次打开后可以使用 Safari 的“添加到主屏幕”。应用会优先从本地缓存启动并在后台更新，因此后续打开更快；它不需要服务器，也不上传图片。

## 版本标注

页面右上角徽章显示形如 `v1.0 20260912` 的版本号（主版本 + 发布日期），用于区分设备上正在运行的是哪一版（PWA 有缓存，容易分辨不清）。

**每次改动页面内容时必须同步更新两处**，否则已安装到主屏幕的应用会继续使用旧缓存，徽章反而会误导：

1. `index.html` 里 `.badge` 的日期；
2. `sw.js` 里 `CACHE_NAME` 的版本号（递增，v11 → v12 …）——它一变，Service Worker 的 install 阶段会重新抓取全部资源。

页面已加入自动更新：打开时主动查一次新版本，从后台切回来时再查一次；新版本 Service Worker 一旦接管就自动刷新一次，所以正常使用下不会长期停留在旧版本。仍然遇到"明明改过了却还是旧样子"时，先看右上角徽章的日期对不对；徽章是旧的说明还在跑缓存，关掉标签页重开一次即可。注意**本机可能同时存在旧的源码副本**（例如早期工具留下的工作目录），直接用浏览器打开那种副本看到的是旧算法，请以线上地址或最新克隆为准。

## 图标

电脑书签、手机书签、手机主屏幕和网页预览统一使用深黑底、白色单字“裁”，不使用裁剪符号。SVG 字形已转为路径，所有 PNG 和 ICO 均来自同一字形，避免依赖设备字体。

图标生成（macOS，在项目根目录运行）：

```sh
clang -fno-modules -framework Foundation -framework CoreText -framework CoreGraphics -framework ImageIO scripts/generate-icons.m -o /tmp/luban-generate-icons
/tmp/luban-generate-icons
node --test tests/icons.test.mjs
```

图标文件名带有版本号。发布新图标时需要同时更新 HTML、manifest、Service Worker 的引用和缓存版本。浏览器已保存的旧书签图片可能需要重新收藏此项目页面后才会更新，不必清除其他网站的数据。

## 回归验证

静态资源与逻辑单元测试：

```sh
npm test
```

检查静态资源引用、缓存清理规则、边界微调语义与图标像素，不需要任何浏览器。

浏览器端到端回归：需要 Playwright。本机已装 Google Chrome 即可，无需下载浏览器内核：

```sh
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install
npm run test:browser
```

用独立的无头 Chrome 与本地回环 HTTP 服务跑真实页面：覆盖各合成图的裁剪量、滑块自动重算、四边手动微调、方向开关、导出 PNG 的实际尺寸、响应式布局与离线缓存启动，不读取个人浏览器资料。

真实样本回归：需要一批自己拍的截图。**这类素材不入仓库**，用环境变量指向所在目录：

```sh
CROPPER_FIXTURES="$HOME/Pictures/测试截图" npm run test:samples
```

它把该目录下所有 PNG 逐一交给页面里的 `analyzeImage`，打印每个方向的裁剪量，并断言关键样本的数值、以及关掉“界面栏”开关后能回落到改造前的行为。

> **安装依赖报 `EACCES ... Your cache folder contains root-owned files`** 时，是 npm 缓存目录被 root 写过。**不要**为此执行 `sudo chown -R`，改用独立缓存目录即可：
> `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm install --cache /tmp/npm-cache`

> 算法的 Python 镜像与合成用例是开发期工具，**不在本仓库内**。它用 PIL 缩放，浏览器用 canvas 缩放，两者在个别图上会相差 3px（约一个采样行）。**以浏览器结果为准**，镜像只用于快速试参数。
